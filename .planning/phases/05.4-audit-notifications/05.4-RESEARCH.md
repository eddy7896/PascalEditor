# Phase 5.4: Audit Log + Notifications - Research

**Researched:** 2026-05-03
**Domain:** Audit trail (Prisma schema + server actions), in-app notification bell (DB-backed polling), email notifications (Resend/React Email)
**Confidence:** HIGH (stack is already proven in project; patterns are well-established)

---

## Summary

Phase 5.4 adds two separate but related systems: an **audit trail** for team-scoped events (membership changes, project mutations) and a **notification system** that surfaces events to individual users (in-app bell + targeted emails).

The audit trail is a pure write-once append log. All mutation points already exist in the codebase (`changeTeamMemberRole`, `removeTeamMember`, invite accept route, `createProject`, `deleteProject`) — the work is adding `TeamAuditLog` writes at each of those callsites and building a read-only audit page. No third-party library is needed; a hand-written Prisma model is the right approach for this scoped use case.

The in-app notification bell requires a `Notification` model, a server action/API route to fetch unread count + recent items, and a client component. For this scale, **DB polling via React Server Component revalidation** is simpler and more reliable than SSE or WebSockets. The unread count can be shown in the sidebar; clicking the bell opens a dropdown. Marking-as-read is a single server action.

Email notifications extend the already-integrated Resend + React Email stack. Two new templates are needed: role-changed and added-to-team. The trigger points are already known: `changeTeamMemberRole` (for role change email) and the invite accept route (for "added to team" email — the invite email already covers NOTIF-02 at invite time, but success criteria say email when added, i.e., accepted).

**Primary recommendation:** Hand-roll the audit log model (simple append-only, no library needed). Use DB-backed polling for in-app notifications (no WebSockets complexity). Extend existing Resend/React Email patterns for two new email templates.

### Pattern 1: Audit Log Model (append-only events table)
**What:** A single `TeamAuditLog` table with an event type enum and structured payload. Written at every mutation; never updated or deleted.
**When to use:** All team-scoped mutations.

```typescript
// prisma/schema.prisma additions

enum AuditEventType {
  MEMBER_JOINED
  MEMBER_REMOVED
  ROLE_CHANGED
  PROJECT_CREATED
  PROJECT_DELETED
}

model TeamAuditLog {
  id        String          @id @default(cuid())
  teamId    String
  actorId   String?         // null for system events
  targetId  String?         // userId or projectId depending on event
  event     AuditEventType
  meta      Json            @default("{}")  // e.g. { oldRole, newRole, projectName }
  createdAt DateTime        @default(now())

  team      Team            @relation(fields: [teamId], references: [id], onDelete: Cascade)

  @@index([teamId, createdAt(sort: Desc)])
  @@index([teamId])
}
```

```typescript
// lib/audit.ts
import { prisma } from "@/lib/prisma";
import type { AuditEventType } from "@/prisma/generated-client";

export async function writeAuditLog(input: {
  teamId: string;
  actorId?: string;
  targetId?: string;
  event: AuditEventType;
  meta?: Record<string, unknown>;
}): Promise<void> {
  await prisma.teamAuditLog.create({
    data: {
      teamId: input.teamId,
      actorId: input.actorId,
      targetId: input.targetId,
      event: input.event,
      meta: input.meta ?? {},
    },
  });
}
```

### Pattern 2: Notification Model (per-user inbox)
**What:** A `Notification` table scoped to a `userId`. A client-side bell polls on page focus/navigation using `router.refresh()` or periodic refetch.
**When to use:** Events targeted at a specific user (scene duplicated, added to team, role changed).

```typescript
// prisma/schema.prisma additions

enum NotificationType {
  SCENE_DUPLICATED      // someone cloned your marketplace asset
  ADDED_TO_TEAM         // you were added to a team (invite accepted)
  ROLE_CHANGED          // your team role was changed
}

model Notification {
  id        String           @id @default(cuid())
  userId    String
  type      NotificationType
  meta      Json             @default("{}")  // e.g. { teamName, assetTitle, newRole }
  readAt    DateTime?
  createdAt DateTime         @default(now())

  user      User             @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@index([userId, createdAt(sort: Desc)])
  @@index([userId, readAt])
}
```

```typescript
// lib/notifications.ts
import { prisma } from "@/lib/prisma";
import type { NotificationType } from "@/prisma/generated-client";

export async function createNotification(input: {
  userId: string;
  type: NotificationType;
  meta?: Record<string, unknown>;
}): Promise<void> {
  await prisma.notification.create({
    data: {
      userId: input.userId,
      type: input.type,
      meta: input.meta ?? {},
    },
  });
}
```

### Pattern 3: Notification Bell Component (polling)
**What:** A client component that fetches unread count on mount + every ~30s, shows a badge, opens a dropdown on click.
**When to use:** In the dashboard sidebar/nav.

```typescript
// Fetch unread count via Server Action
export async function getUnreadNotificationCount(): Promise<number> {
  const session = await getServerSession(authOptions);
  const userId = (session?.user as { id?: string })?.id;
  if (!userId) return 0;
  return prisma.notification.count({
    where: { userId, readAt: null },
  });
}

export async function getRecentNotifications(limit = 10) {
  const session = await getServerSession(authOptions);
  const userId = (session?.user as { id?: string })?.id;
  if (!userId) return [];
  return prisma.notification.findMany({
    where: { userId },
    orderBy: { createdAt: "desc" },
    take: limit,
  });
}

export async function markAllNotificationsRead(): Promise<void> {
  const session = await getServerSession(authOptions);
  const userId = (session?.user as { id?: string })?.id;
  if (!userId) return;
  await prisma.notification.updateMany({
    where: { userId, readAt: null },
    data: { readAt: new Date() },
  });
}
```

### Pattern 4: Audit writes at mutation callsites
**What:** Call `writeAuditLog()` inside existing server actions and route handlers after the primary mutation succeeds. Fire-and-forget (same pattern as email).


**What:** A `page.tsx` at `/dashboard/teams/[teamId]/audit` that fetches audit log entries, formats them as a timeline. OWNER/ADMIN only (RBAC guard).

### Anti-Patterns to Avoid
- **Audit log via Prisma middleware:** Generic middleware captures all mutations including internal/system ones. Domain-specific callsite writes give cleaner, semantic logs with proper `meta` fields.
- **Real-time SSE for notification bell:** Adds stateful server connections; SSE route handlers in Next.js App Router are complex. DB polling on navigation is sufficient for this use case.
- **Storing rendered HTML in audit log meta:** Store structured data (oldRole/newRole) and format for display in the UI. Never store display strings in the DB.
- **Queuing audit writes in a transaction with the primary mutation:** Audit log write failure should NOT roll back the primary mutation. Use fire-and-forget (`.catch()` only).

## Common Pitfalls

### Pitfall 1: Audit Write Inside Transaction
**What goes wrong:** Wrapping `writeAuditLog()` inside a `prisma.$transaction()` with the primary mutation causes the entire operation to roll back if the audit write fails.
**Why it happens:** Treating audit as mission-critical when it's observability.
**How to avoid:** Always call `writeAuditLog()` after the transaction completes, as fire-and-forget with `.catch()`.
**Warning signs:** `prisma.$transaction([..., prisma.teamAuditLog.create(...)])` pattern.

### Pitfall 2: Notification Bell Blocking Navigation
**What goes wrong:** Bell component fetches synchronously on mount, blocking SSR/hydration or causing layout shift.
**Why it happens:** Treating unread count as blocking data.
**How to avoid:** Initialize with `count = 0`, fetch async after hydration using `useEffect` + server action, or use `Suspense` with a fallback badge.
**Warning signs:** Notification fetch in RSC layout that blocks page render.

### Pitfall 3: Email Sent on Invite, Not on Join
**What goes wrong:** NOTIF-02 says "user receives email when invited" — but success criteria 3 & 4 say "email when role is changed" and "email when added to a new team." The current invite route already sends an invite email; the acceptance route (`/api/teams/invite/accept`) does NOT send a "you've joined" confirmation.
**Why it happens:** Conflating the invite email (already exists) with the "added to team" email.
**How to avoid:** Add a `TeamAddedEmail` send in the accept route after the membership upsert. The invite email and added-to-team email are separate triggers.
**Warning signs:** Only modifying the invite POST route for NOTIF-02.

### Pitfall 4: Actor Identity in Audit Log
**What goes wrong:** `actorId` is null because the session isn't read correctly in the server action context.
**Why it happens:** `getServerSession(authOptions)` used inconsistently; some callsites extract `id` from session differently.
**How to avoid:** Follow the existing pattern: `(session?.user as { id?: string } | undefined)?.id` — matches all existing callsites in `actions.ts`.
**Warning signs:** Audit entries with null actorId for user-initiated events.

### Pitfall 5: Audit Log Page RBAC
**What goes wrong:** Any team member can access `/dashboard/teams/[teamId]/audit`.
**Why it happens:** RBAC guard omitted from new route.
**How to avoid:** Use `requireTeamRole()` (already in `lib/rbac-guards.ts`) at the top of the audit page's data fetch. OWNER and ADMIN only.
**Warning signs:** Page accessible to VIEWER role.

### Pitfall 6: Missing Team Relation on TeamAuditLog
**What goes wrong:** The `Team` model doesn't have the back-relation to `TeamAuditLog`, causing Prisma migration to fail.
**Why it happens:** Adding the model without updating both sides of the relation.
**How to avoid:** Add `auditLogs TeamAuditLog[]` to the `Team` model in schema.prisma.

## Open Questions

1. **Audit log retention / pagination**
   - What we know: No retention policy mentioned in requirements.
   - What's unclear: Should the audit page show all history or cap at N entries? Should old entries be prunable?
   - Recommendation: Default to last 100 entries (take: 100, order by createdAt desc). No deletion mechanism in this phase.

2. **Notification retention**
   - What we know: Success criteria say "dropdown of recent notifications."
   - What's unclear: How many? How long kept?
   - Recommendation: Fetch last 20. No auto-deletion in this phase; mark-as-read is sufficient.

3. **Actor display name in audit log**
   - What we know: `actorId` stored in audit log. User names are on the `User` model.
   - What's unclear: Should the audit log page join user names, or store denormalized name at write time?
   - Recommendation: Join at read time (small team sizes; no staleness concern). Fetch distinct actorIds + targetIds from audit entries, then batch-fetch user names in one query.

4. **Email for NOTIF-02 — invite vs accepted**
   - What we know: Invite email already sends on POST to `/api/teams/invite`. Success criteria say "email when added to a team" (i.e., when membership is confirmed).
   - What's unclear: Do we want both (invite + confirmation)?
   - Recommendation: Add a "You've joined [Team]" email in the accept route. This satisfies success criteria 4 precisely. The invite email (already existing) is pre-join; the new email is post-join. Both are desirable; only the post-join is required by success criteria.
