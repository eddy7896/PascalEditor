# Phase 5.2: RBAC Enforcement + Soft Delete - Research

**Researched:** 2026-04-30
**Domain:** Role-based access control (RBAC) enforcement in server actions, soft delete pattern (deletedAt + query filtering)
**Confidence:** HIGH

---

## Summary

This phase adds two layers of safety to project mutations: (1) RBAC guards that check caller's team role before allowing rename/delete/create operations, and (2) soft-delete archiving so deleted projects are timestamped with `deletedAt` rather than hard-deleted. The codebase already has TeamRole and ProjectRole enums defined, and basic role checks exist in team member operations. Role enforcement in project actions is missing — they only check authentication, not authorization. Soft delete requires adding a `deletedAt` field to the Project schema, a Prisma client extension to auto-filter soft-deleted records from all queries, and an archive/restore action pair. The OWNER/ADMIN distinction for teams is already protected (OWNER cannot be assigned via UI, cannot be demoted), but must be clarified in documentation.

**Primary recommendation:** Create a shared role-guard helper (`lib/rbac-guards.ts`) with functions to check project/team permissions. Use Prisma client extension (not middleware) to auto-exclude soft-deleted projects from all queries. Add `deletedAt DateTime?` to Project schema. Add archive/restore server actions alongside the existing delete action.

### Pattern 1: Role Guard Helper
**What:** A utility function that resolves the caller's role in a team/project context and throws `403 Forbidden` if insufficient permissions.
**When to use:** At the start of any server action that modifies a project or team resource.
**Example:**
```typescript
// lib/rbac-guards.ts
// Source: Codebase inspection — existing team role checks (05-02 PLAN)
import { prisma } from '@/lib/prisma'
import type { TeamRole, ProjectRole } from '@/prisma/generated-client'

export class PermissionError extends Error {
  constructor(message: string = 'Insufficient permissions') {
    super(message)
    this.name = 'PermissionError'
  }
}

export async function requireTeamRole(
  teamId: string,
  userId: string,
  requiredRole: TeamRole
): Promise<TeamRole> {
  const membership = await prisma.teamMember.findUnique({
    where: { teamId_userId: { teamId, userId } },
  })
  
  if (!membership) {
    throw new PermissionError('Not a team member')
  }
  
  // Role hierarchy: OWNER > ADMIN > EDITOR > COMMENTER > VIEWER
  const roleHierarchy: Record<TeamRole, number> = {
    OWNER: 5,
    ADMIN: 4,
    EDITOR: 3,
    COMMENTER: 2,
    VIEWER: 1,
  }
  
  if (roleHierarchy[membership.role] < roleHierarchy[requiredRole]) {
    throw new PermissionError(`Requires ${requiredRole} role`)
  }
  
  return membership.role
}

export async function requireProjectRole(
  projectId: string,
  userId: string,
  requiredRole: ProjectRole
): Promise<ProjectRole> {
  const project = await prisma.project.findUnique({
    where: { id: projectId },
    include: { members: { where: { userId } } },
  })
  
  if (!project) {
    throw new PermissionError('Project not found')
  }
  
  const member = project.members[0]
  if (!member) {
    throw new PermissionError('Not a project member')
  }
  
  // Role hierarchy: OWNER > EDITOR > COMMENTER > VIEWER
  const roleHierarchy: Record<ProjectRole, number> = {
    OWNER: 4,
    EDITOR: 3,
    COMMENTER: 2,
    VIEWER: 1,
  }
  
  if (roleHierarchy[member.role] < roleHierarchy[requiredRole]) {
    throw new PermissionError(`Requires ${requiredRole} role`)
  }
  
  return member.role
}

// Simpler variant: just check if user is on the team
export async function assertTeamMember(
  teamId: string,
  userId: string
): Promise<void> {
  const membership = await prisma.teamMember.findUnique({
    where: { teamId_userId: { teamId, userId } },
  })
  if (!membership) {
    throw new PermissionError('Not a team member')
  }
}
```

Usage in server action:
```typescript
// app/dashboard/actions.ts
export async function deleteProject(projectId: string) {
  const session = await getServerSession(authOptions)
  const userId = (session?.user as { id?: string } | undefined)?.id
  if (!userId) throw new Error('Unauthorized')
  
  // Get project to find team
  const project = await prisma.project.findUnique({
    where: { id: projectId },
    select: { teamId: true },
  })
  if (!project) throw new Error('Project not found')
  
  // Check: caller must be EDITOR or OWNER on the team
  await requireTeamRole(project.teamId, userId, 'EDITOR')
  
  // Then archive (soft delete)
  await prisma.project.update({
    where: { id: projectId },
    data: { deletedAt: new Date() },
  })
  
  revalidatePath('/dashboard')
}
```

### Pattern 2: Prisma Soft Delete Client Extension
**What:** A Prisma client extension that intercepts all queries to Project and auto-excludes soft-deleted records (where `deletedAt IS NOT NULL`).
**When to use:** Once in `lib/prisma.ts`, applied to the global Prisma client singleton. Then all queries automatically filter.
**Example:**
```typescript
// lib/prisma-soft-delete.ts
// Source: Prisma docs — https://www.prisma.io/docs/orm/prisma-client/client-extensions/model
import type { Prisma, PrismaClient } from '@prisma/client'

export function createSoftDeleteExtension(client: PrismaClient) {
  return client.$extends({
    query: {
      project: {
        async $allOperations({ operation, args, query }) {
          // For delete operations, do a soft delete (update deletedAt)
          if (operation === 'delete') {
            return query({
              ...args,
              data: { deletedAt: new Date() },
            })
          }
          
          // For deleteMany operations
          if (operation === 'deleteMany') {
            return query({
              ...args,
              data: { deletedAt: new Date() },
            })
          }
          
          // For all read operations (find, findMany, findUnique, etc.)
          // auto-add WHERE deletedAt IS NULL
          if (
            operation === 'findUnique' ||
            operation === 'findUniqueOrThrow' ||
            operation === 'findFirst' ||
            operation === 'findFirstOrThrow' ||
            operation === 'findMany' ||
            operation === 'count'
          ) {
            // Modify where clause to exclude soft-deleted
            const where = args.where ?? {}
            args.where = {
              ...where,
              deletedAt: null,
            }
          }
          
          return query(args)
        },
      },
    },
  })
}
```

**Usage in lib/prisma.ts:**
```typescript
// lib/prisma.ts
import { PrismaClient } from '@prisma/client'
import { createSoftDeleteExtension } from './prisma-soft-delete'

const globalForPrisma = global as unknown as { prisma: PrismaClient }

export const prisma =
  globalForPrisma.prisma ||
  new PrismaClient()
    .$extends(createSoftDeleteExtension(new PrismaClient()))

if (process.env.NODE_ENV !== 'production') {
  globalForPrisma.prisma = prisma
}
```

**Note:** The extension intercepts all Project operations. To restore a soft-deleted project, use an explicit update:
```typescript
// Restore an archived project (bypass the extension by using a raw query or creating a specific restore function)
await prisma.project.update({
  where: { id: projectId },
  data: { deletedAt: null },
})
```

### Pattern 3: Archive + Restore Actions
**What:** Two separate server actions for safe archival and recovery of projects, distinct from hard delete.
**When to use:** Replace `deleteProject` with `archiveProject`. Add `restoreProject` for recovery.
**Example:**
```typescript
// In app/dashboard/actions.ts

export async function archiveProject(projectId: string) {
  const session = await getServerSession(authOptions)
  const userId = (session?.user as { id?: string } | undefined)?.id
  if (!userId) throw new Error('Unauthorized')
  
  const project = await prisma.project.findUnique({
    where: { id: projectId },
    select: { teamId: true },
  })
  if (!project) throw new Error('Project not found')
  
  // Check: EDITOR or above on the team
  await requireTeamRole(project.teamId, userId, 'EDITOR')
  
  await prisma.project.update({
    where: { id: projectId },
    data: { deletedAt: new Date() },
  })
  
  revalidatePath('/dashboard')
  revalidatePath('/dashboard/projects')
}

export async function restoreProject(projectId: string) {
  const session = await getServerSession(authOptions)
  const userId = (session?.user as { id?: string } | undefined)?.id
  if (!userId) throw new Error('Unauthorized')
  
  // NOTE: This query bypasses the soft-delete extension to find archived projects
  // Use a query that explicitly allows deletedAt != null
  const project = await prisma.project.findUnique({
    where: { id: projectId },
  })
  if (!project) throw new Error('Project not found')
  if (!project.deletedAt) throw new Error('Project is not archived')
  
  await requireTeamRole(project.teamId, userId, 'EDITOR')
  
  await prisma.project.update({
    where: { id: projectId },
    data: { deletedAt: null },
  })
  
  revalidatePath('/dashboard')
}
```

### Anti-Patterns to Avoid
- **Checking role without looking up team membership:** A user could be on multiple teams with different roles. Always fetch the specific team membership before allowing mutations.
- **Soft delete extension that breaks unique constraints:** If the Project table has a unique constraint on `(teamId, name)`, soft-deleted projects will still consume the name space. Add a composite unique constraint: `@@unique([teamId, name, deletedAt])` with a partial index `WHERE deletedAt IS NULL` (requires database-level support).
- **Forgetting to update dashboard queries:** The soft-delete extension only works if the Prisma client is the one making queries. Raw SQL or custom queries will return soft-deleted records. Stick to Prisma client for all Project queries.
- **Calling `deleteProject` when you mean `archiveProject`:** The UI should only expose archive/restore. If you have a hard-delete endpoint, gate it severely (admin only, after explicit confirmation).

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Role checking on every action | Custom if statements checking role enums | `requireTeamRole()` + `requireProjectRole()` helpers | Encapsulates hierarchy logic, consistent error handling, reusable |
| Auto-excluding soft-deleted records | Manual `WHERE { deletedAt: null }` in every query | Prisma client extension | Extension is applied once; manual approach is error-prone and repetitive |
| Soft delete filtering for nested relations | Custom query logic to exclude deleted in includes | Prisma extension handles it transparently | Extension interceptsnestedinclude operations |
| RBAC role hierarchy | Nested if statements for each role | Role hierarchy map + numeric comparison | Maintainable, easy to add new roles, clear precedence |

**Key insight:** Role checks and soft delete filtering look simple ("just check a field"), but proliferating these checks across dozens of server actions and queries introduces subtle bugs (missing filters, inconsistent access checks). Centralizing them in helpers and extensions prevents those bugs.

## Common Pitfalls

### Pitfall 1: Role check without team lookup
**What goes wrong:** Action checks `session?.user?.id` exists but then tries to mutate a project without verifying the caller is on the team.
**Why it happens:** Assumes authentication implies authorization. A user authenticated to the app could still be a VIEWER on the team trying to delete a project.
**How to avoid:** Every project mutation must fetch the project's `teamId`, then call `requireTeamRole(teamId, userId, minimumRole)`.
**Warning signs:** Unauthorized users can delete/rename projects they shouldn't access.

### Pitfall 2: Soft delete extension breaks unique constraints
**What goes wrong:** A user publishes "My Design" as a project. Later deletes it (soft-deleted, still in DB). Tries to create a new project with the same name on the same team. Unique constraint violation (composite index doesn't account for `deletedAt`).
**Why it happens:** Database unique constraint doesn't exclude soft-deleted rows.
**How to avoid:** If using unique constraints on Project fields (e.g., `@@unique([teamId, name])`), replace with a partial unique constraint that excludes soft-deleted: add `WHERE deletedAt IS NULL` at the database level. For Prisma, this requires a migration with a raw SQL block.
**Warning signs:** "Unique constraint violation" errors after archiving projects with conflicting names.

### Pitfall 3: Soft delete extension intercepts `delete` → `update` transparently
**What goes wrong:** UI calls `archiveProject()` expecting it to soft-delete, but the action calls `prisma.project.delete()`. The extension converts it to an update, but the UI code assumes hard-delete and tries to refresh data incorrectly.
**Why it happens:** Extension modifies the mutation at the Prisma level, but if the action name/behavior is misnamed, it's confusing.
**How to avoid:** Be explicit: create separate `archiveProject()` and never use `prisma.project.delete()` anywhere. If hard-delete is needed (admin only), create a separate `hardDeleteProject()` that uses raw SQL or bypasses the extension.
**Warning signs:** Archived projects seem deleted but still appear in queries; tests fail because assumptions about delete behavior are wrong.

### Pitfall 4: Restoring an archived project doesn't fetch it from DB correctly
**What goes wrong:** `restoreProject(projectId)` is called but the Prisma soft-delete extension filters out archived projects, so `findUnique()` returns null.
**Why it happens:** The extension is always active, even when you want to find archived records for restoration.
**How to avoid:** For restore operations, you must explicitly query without the filter. Options: (a) Add a `$allOperations` handler that checks for a special flag/context, (b) use a separate raw SQL query, or (c) accept that restore requires fetching from an "archive" page that has its own query bypassing the extension.
**Warning signs:** Can't restore archived projects; "Project not found" error when trying to restore.

### Pitfall 5: Team OWNER cannot be demoted, but this isn't enforced on Project OWNER
**What goes wrong:** The code prevents demoting a team OWNER but allows changing a project OWNER's role via `changeProjectMemberRole()` (if that action exists).
**Why it happens:** OWNER protection is hardcoded only in team member actions; not replicated for project members.
**How to avoid:** If project ownership is ever changeable, protect it the same way: check `if (targetRole === 'OWNER') throw new Error('Cannot change OWNER role')`. For now, projects inherit ownership from the team context, so this is less critical — but document it clearly.
**Warning signs:** Project OWNER roles can be changed when they shouldn't be.

### Pitfall 6: Missing call to `revalidatePath` after soft delete
**What goes wrong:** User archives a project, but it still appears in their dashboard because the Next.js cache isn't invalidated.
**Why it happens:** Soft delete doesn't delete the database row, so if the revalidate is forgotten, the old cached page is served.
**How to avoid:** Always call `revalidatePath('/dashboard')` and `revalidatePath('/dashboard/projects')` after archive/restore, just like hard delete requires.
**Warning signs:** Archived project still visible after refresh or in a new browser tab.

### Pitfall 7: RBAC-guards throws PermissionError, but UI doesn't handle 403 gracefully
**What goes wrong:** User clicks "Delete" on a project, the action throws `PermissionError`, but the error surfaces as a generic server error instead of "You don't have permission to delete this project".
**Why it happens:** Error is thrown server-side but the client doesn't distinguish between auth errors, permission errors, and other failures.
**How to avoid:** Wrap the action call in the UI with error handling: catch the error, check if it mentions "permission" or "Insufficient", and show a user-friendly message. Or return `{ success: false, error: 'message' }` from the action instead of throwing.
**Warning signs:** Users see "Server error" instead of "Permission denied" after clicking delete.

## Open Questions

1. **Unique constraint handling for soft-deleted projects**
   - What we know: Composite unique constraints don't account for `deletedAt`
   - What's unclear: Does the codebase enforce unique project names per team? (Appears optional from schema inspection)
   - Recommendation: If names are NOT currently unique, no action needed. If they become unique later, add a partial unique constraint at the database level: `ALTER TABLE "Project" ADD CONSTRAINT project_team_name_unique UNIQUE (teamId, name) WHERE deletedAt IS NULL`

2. **Hard delete vs. soft delete — when to hard-delete?**
   - What we know: Soft delete is safe and reversible
   - What's unclear: Should there be an admin endpoint to permanently delete archived projects after N days?
   - Recommendation: For v1, soft delete only. In v2 (after audit log is added in 5.4), add an admin function to hard-delete projects older than 90 days.

3. **Restore UI — where should archived projects be visible?**
   - What we know: Soft-delete extension hides them from normal dashboard queries
   - What's unclear: Does the dashboard have an "Archived" section, or is restore only via a separate archive management page?
   - Recommendation: For v1, omit restore from UI. Archived projects stay in DB but hidden. In v2, add `/dashboard/archived` page with a separate query that explicitly includes `deletedAt: { not: null }`.

4. **ProjectRole in database vs. inherited from TeamRole**
   - What we know: Project schema has `ProjectMember.role` as `ProjectRole` enum (separate from TeamRole)
   - What's unclear: Should a team VIEWER always be a project VIEWER, or can projects override team roles?
   - Recommendation: For v1, assume projects have independent roles. Enforce in actions: check `ProjectMember.role`, not derived from team role. If projects should inherit team role in future, that's a separate conversation.
