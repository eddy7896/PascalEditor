# Phase 5.1: Email + Auth Hardening - Research

**Researched:** 2026-04-30
**Domain:** Transactional email (Resend), email verification flow (NextAuth v4 + Prisma), rate limiting (ioredis + Redis)
**Confidence:** HIGH

---

## Summary

This phase replaces three v1 "URL-in-response" shortcuts with real production behavior: transactional email via Resend, email verification gating on credentials signup, and Redis-backed rate limiting on auth endpoints. The codebase already has `ioredis` installed and a `lib/redis.ts` singleton, so rate limiting requires no new infrastructure dependencies. The schema already has `User.emailVerified DateTime?` and `PasswordResetToken` — both can be used directly. Two new Prisma models are needed: `EmailVerificationToken`. The middleware is Edge-only (`getToken` only, never Prisma) and must not be changed to add rate limiting — rate limiting must live inside the route handlers themselves.

**Primary recommendation:** Install `resend` and `@react-email/components`. Implement rate limiting as a shared helper using the existing `redis` singleton via an atomic Lua script. Add `EmailVerificationToken` to schema. Wire everything up in route handlers — not in `middleware.ts`.

### Pattern 1: Resend Singleton
**What:** Create a single Resend instance in `lib/email.ts` and export a typed `sendEmail` function.
**When to use:** Every email send — never instantiate Resend inline in route handlers.
**Example:**
```typescript
// lib/email.ts
// Source: https://resend.com/docs/send-with-nextjs
import { Resend } from 'resend'

const resend = new Resend(process.env.RESEND_API_KEY)

export async function sendEmail(opts: {
  to: string
  subject: string
  react: React.ReactElement
}) {
  const { data, error } = await resend.emails.send({
    from: 'Pascal <noreply@your-verified-domain.com>',
    to: opts.to,
    subject: opts.subject,
    react: opts.react,
  })
  if (error) throw new Error(`Email send failed: ${error.message}`)
  return data
}
```

### Pattern 2: Atomic Redis Rate Limiter (Fixed Window)
**What:** A helper that uses an atomic Lua script to increment a counter and set TTL only on first hit, avoiding race conditions between INCR + EXPIRE.
**When to use:** Call at the top of any auth route handler before processing.
**Example:**
```typescript
// lib/rate-limit.ts
// Source: Redis docs on Lua atomicity — https://redis.io/tutorials/howtos/ratelimiting/
import { redis } from './redis'

const RATE_LIMIT_SCRIPT = `
  local key = KEYS[1]
  local limit = tonumber(ARGV[1])
  local window = tonumber(ARGV[2])
  local count = redis.call('INCR', key)
  if count == 1 then
    redis.call('EXPIRE', key, window)
  end
  return count
`

export async function rateLimit(
  key: string,
  limit: number,
  windowSec: number
): Promise<{ allowed: boolean; remaining: number }> {
  const count = (await redis.eval(RATE_LIMIT_SCRIPT, 1, key, limit, windowSec)) as number
  return { allowed: count <= limit, remaining: Math.max(0, limit - count) }
}
```

**Usage in a route handler:**
```typescript
// At top of POST handler, before any business logic
const ip = req.headers.get('x-forwarded-for') ?? 'unknown'
const { allowed } = await rateLimit(`rl:forgot-password:${ip}`, 5, 60)
if (!allowed) {
  return NextResponse.json({ error: 'Too many requests' }, { status: 429 })
}
```

### Pattern 3: SHA-256 Token Hashing (v2 hardening)
**What:** Store `SHA-256(rawToken)` in DB; send raw token in email link. On redemption, hash the incoming token and look up the hash.
**When to use:** For `PasswordResetToken` (v2 hardening listed in STATE.md). Email verification tokens should use same pattern from the start.
**Example:**
```typescript
// Source: Node.js crypto docs — https://nodejs.org/api/crypto.html
import { randomBytes, createHash } from 'node:crypto'

function generateToken(): { raw: string; hashed: string } {
  const raw = randomBytes(32).toString('hex')
  const hashed = createHash('sha256').update(raw).digest('hex')
  return { raw, hashed }
}

// Store `hashed` in DB. Put `raw` in the email link.
// On redemption:
const hashed = createHash('sha256').update(incomingToken).digest('hex')
const record = await prisma.passwordResetToken.findUnique({ where: { token: hashed } })
```

**Note:** `PasswordResetToken.token` field currently stores raw hex. When switching to SHA-256, existing v1 tokens in DB will be invalidated — this is acceptable since they have a 1-hour TTL anyway.

### Pattern 4: Email Verification Flow
**What:** On credentials signup, create an `EmailVerificationToken`, send email. Gated routes check `user.emailVerified`. A `/api/auth/verify-email?token=...` endpoint consumes the token and sets `emailVerified`.
**Key decision:** Do NOT gate at middleware.ts (Edge Runtime + no Prisma). Gate inside the `authorize` callback in `lib/auth.ts` — throw if `emailVerified` is null.

```typescript
// In CredentialsProvider authorize():
if (!user.emailVerified) {
  throw new Error('EMAIL_NOT_VERIFIED')
}
```

The frontend signin page reads this error code from `useSearchParams` (`?error=EMAIL_NOT_VERIFIED`) and shows a "Check your inbox" message.

### Anti-Patterns to Avoid
- **Rate limiting in middleware.ts:** Edge Runtime blocks ioredis — use route handlers only.
- **`incr` + `expire` as separate calls:** Race condition under load. Always use Lua script.
- **Returning reset/invite URLs in API responses:** The entire point of this phase is to remove this. After change, response is just `{ success: true }`.
- **Sending emails synchronously and returning errors on delivery failure:** Resend returns `{ data, error }` — log the error and still return 200 to avoid leaking user existence via timing. For reset specifically, maintain the "always same response" invariant.
- **Using `emailVerified` check in middleware.ts:** Cannot hit Prisma from Edge. Check is in `authorize()` callback.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Email HTML rendering | Custom HTML string templates | `@react-email/components` | React Email handles CSS inlining, dark mode, client compatibility |
| Rate limit storage | In-memory Map/LRU | `redis` singleton (already installed) | In-memory doesn't work across multiple server instances or restarts |
| Email delivery | SMTP/nodemailer setup | `resend` SDK | Zero config, just an API key |
| Token generation | Math.random or UUID | `randomBytes(32).toString('hex')` from `node:crypto` | Cryptographically secure |

**Key insight:** All the hard parts (email rendering, delivery, distributed rate limit state) are already solved by the libraries. Custom solutions introduce client-compatibility bugs and race conditions.

## Common Pitfalls

### Pitfall 1: Resend `from` domain not verified
**What goes wrong:** Emails silently fail or go to spam with `onboarding@resend.dev` as sender (only works for test sends to your own email).
**Why it happens:** Resend requires DNS verification of the sender domain for production sends.
**How to avoid:** Use a verified domain in `from`. For development/testing, Resend allows sending to the account owner's email from `onboarding@resend.dev`. Set `RESEND_FROM_EMAIL` as an env var so it's configurable.
**Warning signs:** `error.name === 'validation_error'` or emails not arriving.

### Pitfall 2: Existing tokens invalidated by SHA-256 migration
**What goes wrong:** Users who requested a password reset during v1 get an "invalid or expired link" error after v2 deploys.
**Why it happens:** Old DB entries store raw hex; lookup now searches by hash.
**How to avoid:** Do a one-time cleanup — delete all existing `PasswordResetToken` rows on deploy, or add a migration that truncates the table. TTL is 1 hour so impact window is small.
**Warning signs:** All existing reset tokens fail immediately after deploy.

### Pitfall 3: Email verification blocks Google OAuth users
**What goes wrong:** Google OAuth sign-ins fail because `emailVerified` is null on newly created Google accounts.
**Why it happens:** The `signIn` callback creates the user via upsert without setting `emailVerified`.
**How to avoid:** In the `signIn` callback for Google provider, set `emailVerified: new Date()` when upserting. Google has already verified the email — trust it.

### Pitfall 4: Rate limiter key collision
**What goes wrong:** Login rate limit also blocks forgot-password requests from the same IP.
**Why it happens:** Using plain IP as key without endpoint prefix.
**How to avoid:** Prefix keys by endpoint: `rl:login:{ip}`, `rl:signup:{ip}`, `rl:forgot-password:{ip}`.

### Pitfall 5: `RESEND_API_KEY` missing at build time
**What goes wrong:** Build fails or runtime error on first email send.
**Why it happens:** env var not set in deployment environment.
**How to avoid:** Guard the singleton: `if (!process.env.RESEND_API_KEY) throw new Error('RESEND_API_KEY is not set')`. Fail fast at startup.

### Pitfall 6: Email verification token not cleaned up
**What goes wrong:** `EmailVerificationToken` table grows unboundedly.
**Why it happens:** Expired/unused tokens are never deleted.
**How to avoid:** Delete the token row on successful verification. Add a cron or delete-on-create cleanup for tokens older than 24h (can be deferred to v3 — at minimum, delete on use).

## Open Questions

1. **Verified sender domain for Resend**
   - What we know: Resend requires DNS verification for production sends to arbitrary recipients
   - What's unclear: Which domain to use (`archly.cloud`? another?)
   - Recommendation: Make `RESEND_FROM_EMAIL` an env var; use `onboarding@resend.dev` as default for dev/test (only delivers to Resend account owner email — acceptable for dev). Block deployment to prod without `RESEND_FROM_EMAIL` set to a verified domain.

2. **Rate limit values (numbers are illustrative — tune to product)**
   - What we know: 5 attempts / 60 seconds is a common starting point for auth endpoints
   - What's unclear: Whether tighter limits (3/60) are better for this audience
   - Recommendation: Use 5/60 for forgot-password and signup (lower frequency), 10/60 for login (legitimate users may retry quickly on mistype).

3. **Email verification for existing users (pre-phase users have `emailVerified: null`)**
   - What we know: All existing credential-signup users have `emailVerified: null` in DB
   - What's unclear: Should existing users be forced to verify, or grandfathered in?
   - Recommendation: Grandfather existing users — run a migration `UPDATE "User" SET "emailVerified" = "createdAt" WHERE "password" IS NOT NULL AND "emailVerified" IS NULL`. This avoids locking out real current users.
